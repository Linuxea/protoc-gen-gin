错误翻译官

两个世界各说各的错误黑话——总得有人带着对照表

两个世界的错误方言

gRPC 报错不说「404」，它说「code 5」。HTTP 世界正相反。这就像两个国家的外交部：都在描述同一件倒霉事，用的却是各自的公文编号。

🔒

gRPC：数字密码

3 = 参数不合法，5 = 找不到，14 = 服务暂不可用……共 17 个标准 状态码，机器好读，人看不懂。

🌐

HTTP：全网通用的红绿灯

400 请求有误、404 没找到、503 暂时歇菜……每个浏览器、每个前端框架都认识它们。

前端同学拿到 code 5 会一脸茫然，拿到 404 却立刻明白。ginruntime 包里的那张对照表，就是翻译官的字典。

翻译官的工位

整张字典加上翻译流程，一共 53 行。核心是这位 HTTPStatus——每个生成 handler 出错时都会来敲它的门：

CODE · ginruntime/runtime.go 
func HTTPStatus(err error) (httpStatus int, grpcCode int32, message string) {
	if err == nil {
		return http.StatusOK, 0, ""
	}
	st, _ := status.FromError(err)
	httpStatus, ok := grpcToHTTP[st.Code()]
	if !ok {
		httpStatus = http.StatusInternalServerError
	}
	return httpStatus, int32(st.Code()), st.Message()
}
人话翻译

「进门的必须是个错误，还要能拆出三样东西：HTTP 码、gRPC 码、人话说明。」

「没出错？那不用翻译，直接 200 放行。」

「status.FromError 是拆信封：不管错误包了多少层，都把里面的 gRPC 错误抽出来。」

「拿 gRPC 码查字典 grpcToHTTP。查不到？兜底 500——翻译官永远不空手而归。」

「三样东西一起交还：状态码给浏览器看，gRPC 码留作凭据，message 给人读。」

💡
「aha」时刻

注意「兜底 500」这个细节——这是防御式设计的缩影：翻译官自己绝不能成为新的故障点。遇到不认识的错误，宁可报个笼统的 500，也不能崩掉或吞掉。边界层代码的第一美德是「不添乱」。

H
Gin Handler

电话里报错了。前端听不懂「码 5」——HTTPStatus 翻译官，麻烦了！

译
HTTPStatus（翻译官）

拆信封……gRPC 码 5。查字典：5 → 404。打包：HTTP 404 + {code: 5, message: “user 99 not found”}。

浏
浏览器（前端）

404 + code 5——看懂了，是「用户不存在」！弹个友好提示：查无此人 🙂

?

为什么错误体里还留着 gRPC 码？

404 已经说明「没找到」了，响应体里的 {"code":5,...} 是不是多余？不多余——它俩分工不同：

HTTP 404 给机器看的红绿灯：浏览器、网关、监控全靠它路由和告警
"code": 5 给前端逻辑用的精确凭据：多个服务共用一套码，排查时能对上 gRPC 侧的日志
"message" 给人读的一句话说明：直接弹给用户也不丢人
🧩
顺便说一句

这张对照表不是发明的，是抄行业标杆 grpc-gateway 的（Google 官方的同类项目）。跟大部队用同一张表，前端就少学一套方言——选约定俗成，往往优于自作聪明。
