protoc 怎么找到插件？一场从不见面的合作

protoc 和插件的合作方式很特别——像一位从不见面的顾问：protoc 把你的合同卷宗从门缝下塞进去（ 标准输入）， 顾问在屋里干活，把写好的文件从门缝下塞回来（ 标准输出）。

protoc 怎么知道该请哪位顾问？靠命名约定：可执行文件必须叫 protoc-gen-gin（前缀 protoc-gen 是暗号），放在 PATH 目录里。命令行写 --gin_out，它就去请 protoc-gen-gin。

CODE · main.go 
protogen.Options{
	ParamFunc: flag.CommandLine.Set,
}.Run(func(gen *protogen.Plugin) error {
	gen.SupportedFeatures = uint64(pluginpb.CodeGeneratorResponse_FEATURE_PROTO3_OPTIONAL)
	for _, f := range gen.Files {
		if !f.Generate {
			continue
		}
		internal.GenerateFile(gen, f)
	}
	return nil
})

「aha」时刻

插件世界里有一条万能公式：入口越小，规矩越硬，生态越稳。stdin 进、stdout 出、命名约定找人——正因为规矩简单到无聊，任何语言写的插件都能挂上 protoc 这辆车。这种思路叫 管道组合。

为什么需要「零件箱」？

一个自然的疑问：为什么不把 Error 类型和翻译表直接写进每个生成文件？试试就懂了——同一个 包里出现两个同名类型，编译器当场报错：

💥

写进每个生成文件？

一份 proto 生成一个文件。用户的项目往往有几十份 proto——同一个包里塞进几十个同名 Error，编译直接爆炸。

✅

放进共享零件箱？

零件只造一份，所有生成文件 import 它。还能顺手给 swag 一个统一引用——文档里的错误体定义只出现一次。

🧩
顺便说一句

这个包名 ginruntime 是精心挑的——项目笔记里明确记录：不能改回 runtime，否则和 Go 标准库的 runtime 撞名，swag 解析注解时会静默产出错误的文档。改名的代价，往往藏在很远的地方。
