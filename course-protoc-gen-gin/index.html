protoc-gen-gin：会写代码的机器
01

这个项目是干嘛的

一台「会写代码的机器」：把 gRPC 服务自动翻译成 HTTP 接口

两种插座，一个世界

想象你带着笔记本电脑出国：你的插头是国标，墙上的插座是欧标。电是一样的电，形状对不上。

后端世界也有两种「插座」：服务内部用 gRPC 通话，而网页、手机 App、外部合作伙伴只会说 HTTP。

⚡

gRPC：内部高速电话线

微服务之间互相调用用它在行——快、强类型、自带错误码。但浏览器说不了这门方言。

🌐

HTTP + JSON：世界通用语

任何前端、任何第三方都能发一个 JSON 请求过来。慢一点，但谁都会用。

这个项目就是那个转换插头：它自动生成一层翻译代码，让每个 gRPC 方法都能被 HTTP 调用。

怎么做到的？读合同，吐代码

每个 gRPC 服务都始于一份 .proto 合同文件。 这个项目是一个 protoc 插件： 编译合同时，它在旁边加产一批 Go 文件。

注意：HTTP 世界从头到尾没有直接碰过业务逻辑。所有活儿都转交给 gRPC 服务端——这就是「适配层」的含义。

机器吐出来的代码长什么样

这是生成文件 user.gin.pb.go 里的真身（一字未改）。左边是 Go 代码，右边是人话：

CODE · user.gin.pb.go 
func UserServiceGetUserHandler(cli UserServiceClient) gin.HandlerFunc {
	return func(c *gin.Context) {
		var req GetUserRequest
		if err := c.ShouldBindJSON(&req); err != nil && !errors.Is(err, io.EOF) {
			c.JSON(http.StatusBadRequest, ginruntime.Error{Code: 3, Message: "invalid request: " + err.Error()}) // 3 = codes.InvalidArgument
			return
		}
		resp, err := cli.GetUser(c.Request.Context(), &req)
		if err != nil {
			httpStatus, code, message := ginruntime.HTTPStatus(err)
			c.JSON(httpStatus, ginruntime.Error{Code: code, Message: message})
			return
		}
		c.JSON(http.StatusOK, resp)
	}
}
人话翻译

「造一个接待员。他手里握着一位 gRPC 客户端（cli），专门负责 GetUser 这件事。」

「来客人了。先准备一个空表格 req，用来装客人带来的数据。」

「把 JSON 请求体填进表格。如果填不进去（格式错误）——当场退货 400。唯一的例外：客人一个字都没带（io.EOF），算空表格，放行，让服务端去校验。」

「表格合格。拿着它给 gRPC 服务端打电话，等答复。」

「电话里报错了？找翻译官 HTTPStatus 把 gRPC 的错误黑话翻译成 HTTP 状态码，包成统一错误体退回去。」

「一切顺利：答复原样打包成 200 + JSON，交给客人。接待完成。」

🧩
顺便说一句

文件名里的 .pb.go 后缀是 Protocol Buffers 生成代码的行业惯例——一眼就知道「这是机器写的，别手改」。手改了，下次生成会被无情覆盖。

protoc 怎么找到插件？一场从不见面的合作

protoc 和插件的合作方式很特别——像一位从不见面的顾问：protoc 把你的合同卷宗从门缝下塞进去（ 标准输入）， 顾问在屋里干活，把写好的文件从门缝下塞回来（ 标准输出）。

protoc 怎么知道该请哪位顾问？靠命名约定：可执行文件必须叫 protoc-gen-gin（前缀 protoc-gen 是暗号），放在 PATH 目录里。命令行写 --gin_out，它就去请 protoc-gen-gin。

CODE · main.go 
protogen.Options{
	ParamFunc: flag.CommandLine.Set,
}.Run(func(gen *protogen.Plugin) error {
	gen.SupportedFeatures = uint64(pluginpb.CodeGeneratorResponse_FEATURE_PROTO3_OPTIONAL)
	for _, f := range gen.Files {
		if !f.Generate {
			continue
		}
		internal.GenerateFile(gen, f)
	}
	return nil
})
人话翻译

「protogen 是官方给的接待框架：它替你从门缝收卷宗、拆包、整理成好用的结构。」

「这句是在报名单：本插件看得懂 proto3 的 optional 特性——一种合同语法。」

「卷宗里有一摞合同文件。逐份过目……」

「没点名要生成的（比如只是被引用的依赖合同），跳过。」

「点名的，送去车间：GenerateFile，开工。」

为什么需要「零件箱」？

一个自然的疑问：为什么不把 Error 类型和翻译表直接写进每个生成文件？试试就懂了——同一个 包里出现两个同名类型，编译器当场报错：

💥

写进每个生成文件？

一份 proto 生成一个文件。用户的项目往往有几十份 proto——同一个包里塞进几十个同名 Error，编译直接爆炸。

✅

放进共享零件箱？

零件只造一份，所有生成文件 import 它。还能顺手给 swag 一个统一引用——文档里的错误体定义只出现一次。

🧩
顺便说一句

这个包名 ginruntime 是精心挑的——项目笔记里明确记录：不能改回 runtime，否则和 Go 标准库的 runtime 撞名，swag 解析注解时会静默产出错误的文档。改名的代价，往往藏在很远的地方。

模具本体：打印，而不是思考

车间里没有智能，只有一行行 g.P()——「print，往文件里打印一行字」。名字从合同里来，模板是写死的：

CODE · internal/generator.go 
g.P("func " + name + "(cli " + client + ") " + handlerFunc + " {")
g.P("\treturn func(c *" + ctxType + ") {")
g.P("\t\tvar req " + reqType)
g.P("\t\tif err := c.ShouldBindJSON(&req); err != nil && !" + errorsIs + "(err, " + ioEOF + ") {")
g.P("\t\t\tc.JSON(" + badRequest + ", " + runtimeErr + "{Code: 3, Message: \"invalid request: \" + err.Error()}) // 3 = codes.InvalidArgument")
g.P("\t\t\treturn")
g.P("\t\t}")
g.P("\t\tresp, err := cli." + m.GoName + "(c.Request.Context(), &req)")
g.P("\t\tif err != nil {")
g.P("\t\t\thttpStatus, code, message := " + runtimeHTTPStatus + "(err)")
g.P("\t\t\tc.JSON(httpStatus, " + runtimeErr + "{Code: code, Message: message})")
g.P("\t\t\treturn")
g.P("\t\t}")
g.P("\t\tc.JSON(" + okStatus + ", resp)")
g.P("\t}")
g.P("}")
人话翻译

「打印函数的第一行。name 是合同里拼好的名字，比如 UserServiceGetUserHandler——模具只是把名字嵌进固定句式。」

「打印接待逻辑：准备请求表格、解析 JSON、不合格退货 400……」

「注意这一行的秘密：Code: 3 是写死的。gRPC 世界里 3 号错误表示「参数不合法」——下一模块会认识全部错误黑话。」

「打印拨号那行：cli. + m.GoName。GetUser 方法就拨 GetUser，UpdateUser 就拨 UpdateUser——模具不关心拨给谁。」

「错误找翻译官 HTTPStatus，成功就打包 200 返回。每个 handler 的下半场永远一模一样。」

看明白了吗？你在 Module 1 读过的那个 handler 函数，就是这 16 行打印出来的成品。模具里的每一行字，对应成品里的一行代码。

💡
「aha」时刻

读生成式代码的诀窍：别追机器，追模具。成品有一万个，模具只有一套。想理解（或修改）所有 handler 的行为，只需要读这 16 行。

车间里的三个聪明设计

模具简单，但车间并不傻。三个细节值得抄进你的笔记本：

🌊

流式方法：跳过，但大声说

流式方法装不进 HTTP 一问一答，直接跳过——但警告写两遍：控制台 stderr 一遍，生成代码里留一行 WARNING 注释。静默跳过是坑用户，大声跳过是尊重用户。

💬

合同注释，直达文档

proto 里写给同事看的方法注释（// GetUser 根据 ID 获取用户），被原样搬进 @Description，最终出现在 Swagger 文档上。写一遍，处处生效。

📭

空请求体：放行不报错

严格来说空 body 是非法 JSON，但被 io.EOF 例外放行——当成「空表格」交给服务端校验兜底。对调用方宽容一分，集成就顺一分。

「注释直达文档」的实现只有 4 行——这是整个车间我最喜欢的一段：

CODE · internal/generator.go 
g.P("// @Summary      " + m.GoName)
for _, line := range commentLines(m.Comments) {
	g.P("// @Description  " + line)
}
g.P("// @Router       " + route + " [post]")
人话翻译

「文档摘要 = 方法名。」

「合同里这个方法的每一条注释，逐行搬进 @Description——你在 proto 里写的『id 为必填』会出现在 API 文档里。」

「最后印上路由地址和请求方式。注解和代码同生同灭，永不漂移。」

注解：藏在注释里的文档

生成代码的函数上方有一坨 // @Summary ... 格式的注释——这不是普通注释，是 swag 注解。 它们是给机器看的：

@Summary 接口名——文档目录里的一行标题
@Description 接口说明——内容来自你在 proto 里写的注释
@Param / @Success 请求长什么样、成功返回什么——前端照着填表
@Router 地址 + 请求方式——HTTP 世界的门牌号

业务侧跑一遍 swag init --parseDependency，这些注解就变成 swagger.json，再挂一个网页——前端同学就有了可交互的接口说明书。

🧩
顺便说一句

项目笔记里有一条硬约束：handler 必须保持为顶层具名函数。swag 只认「包级函数声明上方的注释」——要是图时髦改成嵌套函数或闭包，注解会全部静默失效。文档工具认死理，代码就得迁就它。

04

错误翻译官

两个世界各说各的错误黑话——总得有人带着对照表

两个世界的错误方言

gRPC 报错不说「404」，它说「code 5」。HTTP 世界正相反。这就像两个国家的外交部：都在描述同一件倒霉事，用的却是各自的公文编号。

🔒

gRPC：数字密码

3 = 参数不合法，5 = 找不到，14 = 服务暂不可用……共 17 个标准 状态码，机器好读，人看不懂。

🌐

HTTP：全网通用的红绿灯

400 请求有误、404 没找到、503 暂时歇菜……每个浏览器、每个前端框架都认识它们。

前端同学拿到 code 5 会一脸茫然，拿到 404 却立刻明白。ginruntime 包里的那张对照表，就是翻译官的字典。

翻译官的工位

整张字典加上翻译流程，一共 53 行。核心是这位 HTTPStatus——每个生成 handler 出错时都会来敲它的门：

CODE · ginruntime/runtime.go 
func HTTPStatus(err error) (httpStatus int, grpcCode int32, message string) {
	if err == nil {
		return http.StatusOK, 0, ""
	}
	st, _ := status.FromError(err)
	httpStatus, ok := grpcToHTTP[st.Code()]
	if !ok {
		httpStatus = http.StatusInternalServerError
	}
	return httpStatus, int32(st.Code()), st.Message()
}
人话翻译

「进门的必须是个错误，还要能拆出三样东西：HTTP 码、gRPC 码、人话说明。」

「没出错？那不用翻译，直接 200 放行。」

「status.FromError 是拆信封：不管错误包了多少层，都把里面的 gRPC 错误抽出来。」

「拿 gRPC 码查字典 grpcToHTTP。查不到？兜底 500——翻译官永远不空手而归。」

「三样东西一起交还：状态码给浏览器看，gRPC 码留作凭据，message 给人读。」

💡
「aha」时刻

注意「兜底 500」这个细节——这是防御式设计的缩影：翻译官自己绝不能成为新的故障点。遇到不认识的错误，宁可报个笼统的 500，也不能崩掉或吞掉。边界层代码的第一美德是「不添乱」。

为什么错误体里还留着 gRPC 码？

404 已经说明「没找到」了，响应体里的 {"code":5,...} 是不是多余？不多余——它俩分工不同：

HTTP 404 给机器看的红绿灯：浏览器、网关、监控全靠它路由和告警

"message" 给人读的一句话说明：直接弹给用户也不丢人

怎么证明它没坏

一台写代码的机器，更需要证明自己写出来的代码是对的

一出话剧的三种检查

剧场排一出戏：裁缝检查每道缝线（部件级）、全组带妆彩排（整体级）、首演见观众（生产环境）。

缝线再完美，也代替不了彩排——但没人愿意把问题留到首演。软件测试同理，而且这个项目把「彩排」做到了极致：整条 HTTP → gRPC 链路在测试里完整跑通，却不占用任何网络端口。

💡
「aha」时刻

生成代码的测试有个天然优势：模具只有一套，所以测一个等于测全部。手写代码要祈祷每个程序员都写对；生成代码只需验证模具——这正是「代码生成」在工程质量上的最大红利。

四道防线

项目布了四层检查，从便宜到昂贵、从局部到整体：

1
单测模具：生成的内容对不对

TestGenerateFileContent 用一份迷你合同跑车间，断言产出包含关键零件：handler 签名、路由行、注解、WARNING 注释——一共 18 条，缺一条就报警。

2
单测字典：翻译对不对

ginruntime 的测试逐条过映射表：NotFound→404、包了一层的错误也能拆开、不认识的兜底 500。8 个 用例，把翻译官钉得死死的。

3
带妆彩排： E2E 全链路

起一个内存里的 gRPC 服务端 + 真实的 gin 引擎，发真 HTTP 请求：200 成功、404 不存在、400 坏 JSON、流式路由必须 404——六幕戏全过。

4
连文档一起验

TestSwaggerDocs 在测试里真的重跑一遍 swag init，然后解析 swagger.json：三条路径必须在、流式方法必须不在、错误体定义必须存在。文档说谎也会被抓。

彩排的秘诀：不占舞台的电话线

E2E 要跑真的 gRPC，难道要在测试里监听真端口？不用。 bufconn 在内存里架线， httptest 在内存里收发 HTTP。看彩排现场怎么搭：

CODE · example/e2e_test.go 
lis := bufconn.Listen(1 << 20)
grpcSrv := grpc.NewServer()
userv1.RegisterUserServiceServer(grpcSrv, &userService{users: map[int64]*userv1.GetUserResponse{
	1: {Id: 1, Name: "alice", Email: "alice@example.com"},
}})
t.Cleanup(grpcSrv.Stop)
go func() { _ = grpcSrv.Serve(lis) }()
人话翻译

「架一根内存电话线（1MB 容量），不走网卡、不占端口。」

「起一个真的 gRPC 服务端——注意，和生产的代码一模一样，不是简化版。」

「业务逻辑就用真的：用户表里预置一个 alice（ID 1）。」

「t.Cleanup 是自动收场：测试结束，服务自动关停，不留垃圾。」

「后台开演。接下来生成的 handler 会拨这根内存线——整条链路无一处是假的，除了网线。」

剧场外的守则

项目笔记（AGENTS.md）里记着几条用真实教训换来的铁律——每条背后都是一次踩坑：

🔒

版本号钉死

go.mod 的 go 1.19 和依赖版本绝不升级——为了老工具链还能一行命令安装。有人跑过新版 tidy，指令被改写成三段式，老 Go 直接装不上。兼容性是承诺，不是偏好。

📦

生成产物入库

user.gin.pb.go 这类生成文件直接 commit 进仓库。使用者不必装插件就能编译。代价是：改了模具必须同步重新生成，否则测试立刻提醒你。

🏷️

发布只走 tag

用户 go install@latest 拉的是 git tag 版本。所以打 tag 的同时必须更新代码里的 Version 常量——版本号写两处，一处是给 git 看的，一处是给生成文件头看的。

带走的一句话

这个项目教的不只是一个插件，而是一种工程哲学：重复的事交给模具，模具的行为交给测试，测试的信心交给你和 AI。下次你让 AI 写二十个相似接口时，可以问它：「这事值得做成代码生成吗？」
